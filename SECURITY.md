# Security maintenance

Production administrators must complete authenticator verification before any management API is available. On first sign-in, confirm the current password, add the displayed manual key to an authenticator app and enter its code. Save all eight recovery codes in a private password manager; they are displayed once and each works once. Keep hosting-account recovery separate. Losing both the authenticator and recovery codes requires a controlled recovery through the private hosting environment; there is no public MFA reset endpoint.

Production sessions use Secure, HttpOnly, SameSite=Strict host-only cookies. This release changes the cookie name, so existing users must sign in again. Administrator sessions expire after 30 idle minutes or eight hours; customer sessions after 24 idle hours or seven days. Password changes and the security panel's sign-out-all action revoke existing sessions. Public registration cannot grant an administrator role.

Owner provisioning requires a private random setup token and is disabled once an administrator exists. File-backed tokens expire 24 hours after creation. If provisioning expires before the first owner is created, run `npm run admin:setup -- --rotate` privately inside the host, then restart the application. Environment-provided tokens must be rotated in hosting configuration. Never publish setup URLs, tokens, recovery codes or database copies.

The private persistent volume contains `accounts.sqlite`, its WAL files, uploaded assets, `admin-setup.token` and `security.key`. MFA secrets are encrypted with the key; recovery codes and limiter identities are keyed hashes. Back up SQLite using its backup facility, together with uploads and **security.key**, to private storage. A database without this key cannot decrypt MFA secrets. Encryption does not protect against an attacker who controls the host and key. Automated off-host backups are not configured by this change.

Authentication and API rate limits persist across restarts and retain bounded records. Security audit storage retains the newest 10,000 events; the panel shows the newest 100. Events store identifiers and routes, not passwords, email addresses, recovery codes or request bodies. Uploaded raster images must match their declared file type, pass size/dimension checks and are re-encoded as WebP. SVG decoding is blocked. Uploaded media has a 200 MB application quota on the current 500 MB volume.

Responses include CSP, anti-framing, MIME sniffing protection, restricted browser permissions and production HSTS. Executable inline scripts are forbidden. Existing inline styles and Google Fonts remain allowed. Private files, the raw seed catalogue and unexpected static file types are not served. In the Railway container, root-mounted volume permissions are repaired before the application drops to the non-root node user and begins accepting requests.

Run `npm run check`, `npm run security:check`, `npm run hosting:check` and `npm audit --omit=dev --audit-level=high` before deployment. CI also builds and runs the production image against a root-owned persistent volume. Report vulnerabilities privately to the repository owner; avoid posting credentials or exploitable customer data in public issues.

This is application hardening, not a certification or a guarantee against all attacks. Independent penetration testing, edge WAF/DDoS controls and automated backups remain separate work. Google OAuth credentials, email delivery and actual payment processing remain unconfigured. Search indexing stays disabled until commercial launch data is ready.
